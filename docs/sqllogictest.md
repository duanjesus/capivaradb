# sqllogictest results

[sqllogictest](https://www.sqlite.org/sqllogictest/doc/trunk/about.wiki) is
the corpus SQLite uses to compare itself with other databases: each record
is a statement or a query together with the result every engine should
give. `tools/slt` runs those scripts against CapivaraDB in-process.

This page is generated by `bash scripts/slt.sh --update`; the table below is
the output of the last run. CI runs the same scripts on every push and fails
if any pass count drops below `compat/slt/baseline.txt`.

## How to read the numbers

- **One script per family.** The corpus has hundreds of scripts generated
  from the same templates (`index/between/1/slt_good_0.test` has many
  siblings). One of each kind is run; running them all would add time, not
  information.
- **Records marked for other engines are skipped.** Scripts carry
  `skipif`/`onlyif` directives for dialect differences. CapivaraDB runs as
  `postgresql`, so MySQL-only variants (`DIV`, `CAST(... AS SIGNED)`) are not
  counted, exactly as they would not be for PostgreSQL.
- **Results are compared strictly.** Long results are compared by MD5 of
  every value, so a single wrong row or a wrong sort order fails the record.
- **What these scripts do not exercise.** They were generated for SQLite:
  small tables, integers, floats and text. They say nothing about
  durability, concurrency or performance.

## Not in the regular run

Two scripts are measured separately because they need what the engine does
not have yet. They are kept out of CI only because of how long the failures
take to time out.

| Script | Records | Passed | Why the rest fail |
|---|---:|---:|---|
| `select4.test` | 3857 | 1506 (39.0%) | 1000 use `UNION`/`EXCEPT`/`INTERSECT`, which are not implemented; 1351 time out (300 ms limit) |
| `select5.test` | 1436 | 739 (51.5%) | 697 time out (300 ms limit) |

The timeouts are queries like `FROM t1, t2, t3, t4, t5, t6 WHERE ...`. Joins
run as nested loops in the order written and the `WHERE` clause is applied
only at the end, so the full cross product is built first. Pushing
predicates down and choosing a join order is the planner's job (milestone
6); these two scripts are its benchmark.

## The records that fail

All fifteen are places where the scripts expect SQLite's behaviour and
PostgreSQL itself answers differently, so they are left as they are:

- `1 IN ()` — an empty list is a syntax error in PostgreSQL.
- `x'303132'` — SQLite's blob literal.
- `'hello' IN (SELECT integer_column ...)` — SQLite compares across types;
  PostgreSQL rejects the text as an invalid integer.
- `UPDATE t1 SET x=3, x=4, x=5` — SQLite applies the last assignment;
  PostgreSQL rejects assigning a column twice. The two "wrong result"
  records are queries that depend on that update having happened.
